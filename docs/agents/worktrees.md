# Работа с worktrees

Документ читается, когда задач несколько, когда агентов несколько или когда правку нужно изолировать от рабочей копии клона.

## Зачем

Worktree это дополнительный рабочий каталог того же репозитория на своей ветке. У него общая история с клоном, но свои файлы и свой индекс. Два агента, которые правят один клон в разных worktrees, не затирают чужие файлы и не делят индекс. Одну ветку нельзя открыть в двух worktrees одновременно, git откажет.

В метарепозитории это важнее, чем в обычном репозитории. Правка одного соглашения часто затрагивает несколько шаблонов, и по worktree на каждый клон даёт каждой правке свою ветку, не трогая то, что человек делает в основных клонах.

## Раскладка

```text
ai-metarepo/
├── repos/nodejs-package/                    основной клон, ветка main
└── .worktrees/                              в .gitignore
    └── nodejs-package-fix-lint/             worktree, ветка fix-lint
```

Worktrees лежат в `.worktrees/` внутри метарепозитория, а не рядом с ним. Тогда агент, запущенный в worktree, поднимается по каталогам к `AGENTS.md` метарепозитория (поведение Claude Code по документации, см. [repository-layout.md](repository-layout.md)). Для Codex это явно не описано, проверьте запуском.

## Команды

```sh
mise run worktree nodejs-package fix-lint           # создать
mise run worktree-remove nodejs-package fix-lint    # удалить
git -C repos/nodejs-package worktree list           # посмотреть все
```

Задача `worktree` выполняет `git worktree add` в нужном клоне и печатает путь. Задача `worktree-remove` допускает повторный вызов. Если каталога уже нет, она только выполняет `git worktree prune`. Ветка после удаления worktree остаётся в клоне, её удаляет человек.

## Правила

1. Одна задача, один worktree, одна ветка. Имя ветки описывает задачу и совпадает с суффиксом каталога.
2. Не удаляй каталог worktree через `rm -rf`. Используй `mise run worktree-remove`, иначе git хранит запись о несуществующем worktree до `git worktree prune`.
3. Зависимости в новом worktree не общие. В `node_modules` основного клона они остаются, а в worktree их нет, поэтому после создания выполни `make install` в его каталоге.
4. Локальные файлы вроде `.env` в worktree не копируются, git их не отслеживает. Скопируй нужные файлы руками или перечисли их в `.worktreeinclude`, если используешь встроенное создание worktree в Claude Code.
5. Коммит и push подтверждаются отдельно, как для любого клона (`AGENTS.md`). Коммит в worktree идёт в его ветку, основной клон не меняется.
6. После слияния ветки сделай `mise run worktree-remove`. Worktree сабагента с изменениями Claude Code после завершения работы сохраняет, а периодическая очистка пропускает worktrees, созданные собственным хуком.

## Подготовка среды при создании

В этом репозитории worktree создаёт задача `mise run worktree`, а `make install` запускается руками. Если подготовку нужно автоматизировать, у инструментов есть свои механизмы. Проверено 5 октября 2026 года по официальной документации, перепроверьте перед использованием.

- **Claude Code.** Хук `WorktreeCreate` полностью заменяет создание worktree, обработчик сам создаёт каталог и возвращает путь, встроенное копирование `.worktreeinclude` при этом отключается. Парный `WorktreeRemove` обслуживает удаление. Справочник: [hooks](https://code.claude.com/docs/en/hooks#worktreecreate), [worktrees](https://code.claude.com/docs/en/worktrees).
- **Codex.** В приложении Codex setup script запускается при создании worktree для нового чата. Среда хранится в `.codex`. В справочнике хуков Codex событий `WorktreeCreate` и `WorktreeRemove` не нашлось. Справочник: [local environments](https://learn.chatgpt.com/docs/environments/local-environment).
- **Worktrunk.** Отдельный инструмент с хуками `pre-start`, `post-start`, `pre-remove`, `post-remove`. Хук `post-create` в версии 0.32.0 переименован в `pre-start`. Справочник: [worktrunk.dev/hook](https://worktrunk.dev/hook/).

Документация не обещает вызова очистки при аварийном завершении процесса или при удалении каталога внешней командой. Поэтому команда очистки должна допускать повторный ручной запуск, как `worktree-remove` здесь.

## Типичные ошибки

- Правка в основном клоне, пока в worktree идёт параллельная задача на той же ветке. Git не даст открыть ветку дважды, и это подсказка, а не помеха.
- Запуск `mise run check` из worktree. Проверка ходит по `repos/*`, а worktrees она не видит. Проверяй клон до создания worktree или запускай `ast-grep scan` по каталогу worktree напрямую.
- Забытые worktrees. Список даёт `git -C repos/<имя> worktree list`.
